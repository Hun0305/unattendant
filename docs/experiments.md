# 엣지 AI 실험 설계

Pi 4B에서 소형 LLM과 비전 모델을 직접 돌려 재는 실험의 설계다. 어떤 모델을 고르는지, 무엇을 어떻게 재는지, 측정이 오염되지 않게 무엇을 지키는지, 결과를 어디에 남기는지를 다룬다. 원칙은 [edge-ai-blog-topics.md](edge-ai-blog-topics.md)를 따르고, 진행은 [todo.md](todo.md) Phase 2 "실험 러너와 공통 로거"에서 본다.

2026-10-14 초안이다. 모델 목록과 파일 크기는 같은 날 Hugging Face API로 확인한 값이다. 12절 "정할 것"이 정해지면 날짜와 함께 고친다.

- **순서**: 소형 LLM을 먼저 하고 비전은 그다음에 한다. 카메라가 아직 인식되지 않는다(2026-10-13 확인).
- **대원칙**: 측정 방법(모델 파일, 런타임 빌드, 과제 세트, 지표)은 한 번 정하면 고정한다. 바꿀 때는 새 버전을 만들어 회차끼리 비교되게 한다. Pi 한 대에서 낸 수치는 "참고용 벤치마크"라고 글에 밝힌다.

## 1. 이 실험이 답할 질문

1. Pi 4B 4GB에 어떤 소형 LLM이 들어가나 (메모리)
2. 얼마나 빠른가 (첫 토큰까지 시간, 생성 속도)
3. 쓸 만한가 (좁은 작업의 정확도, 한국어)
4. 무엇이 속도를 바꾸나 (양자화 형식, 스레드 수, 문맥 길이, 모델 구조)
5. 시간이 지나면 어떻게 바뀌나 (런타임 버전, 계절과 온도). 기준 모델을 매달 같은 조건으로 다시 잰다

## 2. 대상 하드웨어와 고정 조건

2026-10-14 실측이다. 측정 때마다 `conditions.json`에 다시 기록한다(9절).

| 항목 | 값 |
| --- | --- |
| 보드 | Raspberry Pi 4 Model B Rev 1.5 |
| CPU | Cortex-A72 4코어, 최대 1.8GHz. 명령어 확장은 NEON(`asimd`)뿐이고 dotprod·i8mm가 없다 |
| 메모리 | 3.8GB, zram 스왑 2GB |
| 저장 | SD카드 64GB (남은 공간 40GB). `/tmp`는 RAM(tmpfs 1.9GB) |
| 냉각 | 방열판과 팬 케이스. 유휴 40°C, 스로틀링 기록 없음(`get_throttled=0x0`) |
| CPU 거버너 | `ondemand`. 바꾸지 않고 기록만 한다(시스템 설정 변경을 피한다). 4코어를 다 쓰는 부하라 바로 최고 클럭으로 오르는지는 로거의 클럭 기록으로 확인한다 |
| OS | Raspberry Pi OS 64비트(Debian 13), 커널 6.12, gcc 14.2, cmake 3.31 |

**Pi 4만의 사정**: llama.cpp의 ARM 최적화 경로(가중치 재배치, repack)는 dotprod나 i8mm가 있어야 켜진다(2026-10-14 소스 `ggml-cpu/repack.cpp`에서 확인). Pi 4는 기본 NEON 경로만 쓴다. 그래서 Pi 5나 폰에서 나온 "어느 양자화 형식이 빠르다"는 결과가 Pi 4에는 맞지 않을 수 있다. 이것 자체가 재 볼 거리다(5.3절).

## 3. LLM 모델

### 3.1 고르는 기준

- 지시형(instruct) 오픈 웨이트 모델이고 GGUF 파일이 있다.
- **upstream llama.cpp 릴리스가 그 구조를 지원한다.** 패치한 빌드가 필요한 모델은 비교에서 뺀다. 빌드가 다르면 같은 조건이 아니다.
- **크기는 이름의 "B"가 아니라 Q4_K_M 파일 크기로 나눈다.** 본 비교는 1.5GB 이하, 한계선 비교는 1.5~2.2GB다. Gemma 4 E2B는 이름이 2B지만 Q4 파일이 3.4GB다.
- GGUF 출처는 제작사 공식 → ggml-org → bartowski 순으로 고른다. 양자화 형식끼리 비교할 때는 한 출처 안에서만 비교한다. 출처마다 imatrix를 쓰는지가 달라서, 모델 간 품질 비교에는 이 차이가 섞인다. 출처를 기록하고 글에 밝힌다.
- 로그인(게이트) 없이 받을 수 있는 저장소를 쓴다. Hugging Face 토큰을 Pi에 두지 않는다(비밀값이 하나 는다).
- 저장소 리비전(커밋)과 파일 sha256을 고정해 기록한다. 같은 이름의 파일이 나중에 바뀌어도 회차 비교가 깨지지 않는다.
- **모델 목록(`experiments/models.toml`)은 사람이 고친다.** Huninn은 등록된 모델 중에서 고르기만 한다. GGUF 파서에서 메모리 취약점이 보고된 적이 있어, 출처를 확인하지 않은 파일을 자동으로 받지 않는다.

### 3.4 기준 모델

**Llama 3.2 1B Instruct Q4_K_M**(sha256 고정)을 매달 같은 조건으로 다시 잰다.

- llama.cpp에서 오래 다듬어진 구조라, 값이 바뀌면 모델보다 환경(런타임, 온도, OS) 쪽 변화로 읽을 수 있다.
- 새 모델을 재는 밤에는 기준 모델도 같이 잰다. 기준 모델 값이 평소 범위 안이면 그날 결과를 다른 회차와 비교할 수 있다.

### 3.6 새 모델이 나오면 (LLM 이벤트 시리즈)

1. 3.1절 기준을 통과하면 운영자가 `models.toml`에 넣는다. Phase 2의 `get_trends`가 신모델 소식을 잡으면 Huninn은 백로그에 제안만 한다.
2. 같은 llama.cpp 빌드로 새 모델과 기준 모델을 같은 밤에 잰다.
3. 1회차 표에 한 줄을 더하는 글과, 지금 1등과 맞대는 글을 쓴다.

## 4. 런타임

- **llama.cpp 릴리스 태그를 고정한다.** 2026-10-14 최신은 `v0.6.0`(2026-10-05)이다. 고정할 수 있고, 상주 데몬이 없어 실험 유닛의 메모리 상한 안에서 시작하고 끝난다.
- Pi에서 소스로 빌드한다(Release, `GGML_NATIVE`). 밤에 `-j3`로 빌드하고, 바이너리는 레포 밖 `~/opt/llama.cpp/<태그>/`에 둔다. 이전 빌드는 지우지 않는다.
- 기록: 태그, 커밋, 컴파일러, cmake 옵션, `system_info` 줄. 이 줄에 `NEON = 1`, `DOTPROD = 0` 같은 값이 그대로 찍혀 2절 사정의 증거가 된다.
- **월 1회 업그레이드**: 최신 릴리스로 빌드하고, 기준 모델을 옛 빌드와 새 빌드로 같은 밤에 잰다. 환경 변화와 런타임 변화를 떼어 볼 수 있다.
- Ollama는 기본 측정에 쓰지 않는다(상주 데몬, 버전·옵션 고정이 어렵다). 같은 GGUF로 llama.cpp와 비교하는 글감으로만 쓴다.

## 5. LLM 측정 방법

### 5.1 지표

| 지표 | 정의 | 도구 | 반복 |
| --- | --- | --- | --- |
| 프롬프트 처리 속도 `pp512` | 512토큰 프롬프트를 읽는 속도(tok/s) | `llama-bench -p 512` | 5회, 평균±표준편차 |
| 생성 속도 `tg128` | 128토큰을 만드는 속도(tok/s) | `llama-bench -n 128` | 5회 |
| 긴 문맥 생성 속도 `tg128@d2048` | 문맥 2048토큰이 찬 뒤의 생성 속도 | `llama-bench -n 128 -d 2048` | 3회 |
| 첫 토큰까지 시간(TTFT) | 요청을 보낸 뒤 첫 토큰이 올 때까지(ms) | `llama-server` 스트리밍, 6절 과제 세트 문항마다 | 문항 수만큼. 중앙값과 p90 |
| 답 하나 걸린 시간 | 요청부터 답 끝까지(s) | 위와 같음 | 위와 같음 |
| 최대 메모리 | 모델+KV 캐시+버퍼(MB) | 작업 프로세스의 최대 RSS. mmap을 끄므로 RSS가 전부다 | 작업마다 |
| 콜드 로드 시간 | 모델 파일을 페이지 캐시에서 비운 뒤 서버가 준비될 때까지(s). SD카드 읽기 속도가 들어간다 | `posix_fadvise(DONTNEED)` 뒤 `llama-server` 기동 | 3회 |
| 과제 정확도 | 6절 | 채점 코드 | 1회(그리디라 결과가 같다) |
| 에너지 | J/토큰, 답 하나당 J | 전력계(8절) | 전력계가 있을 때 |

`pp512`·`tg128`은 llama.cpp 커뮤니티가 쓰는 표준 조건이라, 남의 표와 맞대 볼 수 있다. TTFT와 답 시간은 실제 쓰임에 가까운 값이라 글의 첫 문단에는 이쪽을 쓴다.

### 5.2 공통 고정 설정

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 스레드 | 4 (스레드 실험만 1~4) | 코어 수 |
| 문맥 길이 | 4096 | 실제 쓰임과 메모리 한계 사이 |
| 모델 불러오기 | mmap 끔(`--load-mode`. 정확한 값은 고정한 릴리스의 `--help`로 확인) | 메모리가 모자랄 때 SD카드에서 다시 읽으며 조용히 느려지지 않고, 최대 RSS가 실제 사용량이 된다 |
| KV 캐시, 배치, flash attention | 기본값 그대로, 실제 값을 기록 | 기본값이 사람들이 쓰는 값이다 |
| 측정 전 냉각 | CPU 50°C 이하가 될 때까지 기다림(최대 10분) | 앞 측정의 열이 다음 측정을 깎지 않게 |
| 워밍업 | `llama-bench` 기본 워밍업 1회 | 첫 실행의 캐시 효과를 뺀다 |
| 프롬프트 캐시 | 끔(요청마다 `cache_prompt: false`) | 같은 접두부가 재사용되면 TTFT가 실제보다 짧게 나온다 |

### 5.3 실험 조건 (글감마다 하나씩)

| 조건 | 대상 | 바꾸는 것 | 볼 것 |
| --- | --- | --- | --- |
| 스레드 | 기준 모델(새 구조가 나오면 그 모델도) | 1, 2, 3, 4 | 생성은 메모리 대역폭에 묶여 스레드를 늘려도 덜 오를 것으로 본다. 실제로 잰다 |
| 양자화 | 기준 모델(bartowski) + LFM2.5 1.2B(공식). 각각 한 출처 안에서 | Q4_0, Q4_K_M, Q5_K_M, Q8_0. LFM2.5는 제작사가 낸 QAD(양자화 인지 증류) Q4_0도 | 속도, 메모리, 과제 정확도, 같은 모델 안의 퍼플렉서티(PPL). QAD Q4_0가 같은 크기의 일반 Q4_0보다 나은지 |
| 문맥 길이 | 1회차 8종 | 깊이 0, 2048 | 구조별 생성 속도 저하 |
| 생각 모드 | 생각 모드가 있는 모델(Qwen3.5, EXAONE 4.0) | 끔·켬 | 정확도가 오르는 만큼 몇 배 느려지나 |
| JSON 제약 | 1회차 8종 | 과제 T1을 그냥 / JSON 스키마 제약(llama.cpp 문법) | 형식 오류는 사라지는데 내용 정확도와 속도는 어떤가 |

**퍼플렉서티**: 한국어·영어 위키백과의 고정 리비전 문서 묶음(언어별 약 1만 토큰)으로 잰다. 토크나이저가 다르면 값이 비교되지 않으므로 같은 모델의 양자화끼리만 비교한다. 원본 대비 KL 발산은 기준 로짓 파일이 크다(어휘 수 × 토큰 수, Qwen3.5는 어휘가 24만 개). 데스크탑을 WOL로 붙이면(Phase 3) 더한다.

## 6. 과제 세트 `llm-tasks-v1` (품질)

**원칙**: 자동으로 채점되는 좁은 작업만 쓴다. 온디바이스 LLM이 실제로 쓰이는 곳(분류, 추출, 자연어 → 구조화 명령)이고, 채점에 다른 LLM을 쓰지 않아 비용이 없고 재현된다.

한국어 100문항:

| 과제 | 문항 | 내용 | 채점 |
| --- | --- | --- | --- |
| T1 명령 → JSON | 30 | 차량·집 기기 제어 명령을 정해진 스키마의 JSON으로. 지원하지 않는 요청 5문항 포함(빈 동작과 이유를 내야 정답). [edge-ai-blog-topics.md](edge-ai-blog-topics.md) 3절의 차량 제어 JSON 아이디어 | JSON 파싱 성공, 스키마 통과, 동작 집합이 정답과 같음(순서 무관) |
| T2 의도 분류 | 30 | 문의 문장 → 라벨 5개 중 하나 | 라벨 일치 |
| T3 정보 추출 | 20 | 약속·예약 문자 → 날짜, 시간, 장소, 인원 | 항목별 일치, 전부 일치 |
| T4 짧은 한국어 답 | 20 | 짧은 글을 읽고 한두 문장으로 답 | 필수 키워드 포함, **언어 이탈**(한자·가나 섞임, 영어로 답함) |

언어 이탈은 한국어 블로그만의 지표다. 소형 모델이 한국어 질문에 중국어나 영어를 섞어 답하는 비율이고, 정규식으로 자동으로 잰다.

**돌리는 방식**

- 그리디 디코딩(temperature 0), 고정 seed, 과제별 최대 토큰 수. 최대 토큰에 걸려 잘린 답은 따로 표시한다.
- 모든 모델에 같은 시스템 프롬프트와 예시 2개를 쓰고, 채팅 템플릿은 GGUF에 든 모델 자신의 것을 쓴다.
- 생각 모드는 끈다(Qwen3.5 0.8B는 기본이 꺼짐). 켜는 것은 5.3절 별도 조건이다.
- 제작사 권장 샘플링(예: Qwen3.5 비생각 모드 temperature 1.0)과 다르다는 것을 글에 밝힌다. 재현성을 위해 그리디로 통일했다.
- 처음 한 번은 같은 빌드·같은 스레드로 두 번 돌려 출력이 같은지 확인한다. 같으면 이후 1회만 돈다.
- 걸리는 시간(추정, 시험 실행에서 확인): 1B급 하나에 40~60분, 2B는 그 두 배.

**만들기와 고치기**

- 문항 초안은 개발 세션의 Claude가 쓰고, 정답은 운영자가 한 문항씩 검수한다.
- 공개 레포에 둔다(CC0). 고칠 때는 v1을 고치지 않고 v2를 만든다. 결과마다 과제 세트 버전과 해시를 남긴다.
- 공개된 문항이라 나중 모델이 학습했을 수 있다. 한계로 글에 적는다.

**보고**: 정답 수와 문항 수를 같이 쓴다(예: 23/30). 30문항에서 1~2문항 차이는 우연 범위라 순위를 매기지 않는다.

## 7. 측정을 지키는 규칙

### 7.1 실행 격리

- 실험은 systemd 서비스로만 돈다(CLAUDE.md 규칙). 사용자 `hun`, `MemoryMax=2.5G`(시작값. 밤 시간대 기본 메모리를 잰 뒤 조정), `MemorySwapMax=0`, `OOMScoreAdjust`를 높여 메모리가 모자라면 실험이 먼저 죽게 한다. `Nice`를 줘 블로그 서빙이 우선한다.
- 스왑을 막는 이유: zram으로 새면 실험이 죽지 않고 조용히 느려져 측정값이 오염된다. 차라리 실패하고 실패로 기록하는 편이 낫다.
- 시간대: 02:00~05:30. 14:00 Huninn 사이클과 겹치지 않는다. 비전 촬영(낮)과도 겹치지 않는다. 한 번에 하나만 돈다.
- **사이클이 우선한다.** 반려·접기 직후 사이클(`huninn-cycle-now.path`)은 밤에도 돌 수 있다. 실험 중에 사이클이 시작되면 러너가 지금 측정을 멈추고 "중단: cycle"로 남긴 뒤, 사이클이 끝나면 그 측정을 다시 잰다(시도 횟수로 세지 않는다). 두 서비스의 메모리 상한(2.5G + 1G)에 기본 사용량을 더하면 실제 메모리(3.8GB)를 넘기 때문이다. architecture.md의 "그동안 에이전트 루프는 쉰다"와 반대 방향이라 12절 8번에서 정한다.

### 7.2 시작 조건 (하나라도 안 맞으면 10분 뒤 다시 보고, 시간대가 끝나면 다음 밤으로 미룬다)

- **VS Code 서버 프로세스가 없다**(`~/.vscode-server/` 아래 프로세스). CLAUDE.md "VS Code 원격 연결 중에는 LLM 실험을 돌리지 말 것"의 판정 방법이다. 연결을 끊어도 서버가 한동안 남을 수 있어 연결이 아니라 프로세스를 본다. 2026-10-14 개발 세션 중에는 VS Code 서버와 확장의 Claude 프로세스가 RSS 합계 1GB 넘게 차지했다.
- Huninn 사이클(`huninn-cycle.service`)이 돌고 있지 않다.
- `MemAvailable`이 `MemoryMax` + 300MB 이상이다.
- 1분 부하 평균이 0.5 미만이다.
- CPU 온도 50°C 이하다(최대 10분 기다림).
- 다른 실험이 돌고 있지 않다(잠금 파일 `logs/exp-run.lock`).

실행 중에 VS Code 서버가 뜨면 그 작업을 멈추고, 조건이 다시 맞을 때 처음부터 돈다. 사이클이 시작되면 지금 측정만 멈추고 사이클이 끝난 뒤 다시 잰다(7.1절).

### 7.3 공통 로거 (1초 간격)

CPU 온도, ARM 클럭, `vcgencmd get_throttled`의 현재 비트(저전압, 클럭 제한, 스로틀링, 소프트 온도 제한), `MemAvailable`, 실험 cgroup 메모리, 스왑 입출력(`/proc/vmstat`), major page fault, 전체 CPU 사용률과 그중 실험 프로세스 몫(→ **다른 프로세스 CPU**), 전력계 값(있으면). 실행 중에는 `/tmp`(RAM)에 쓰고 끝나면 결과 폴더로 옮긴다. `get_throttled`의 "발생한 적 있음" 비트는 재부팅 전까지 남으므로 현재 비트를 본다.

### 7.4 무효 조건

측정 구간 안에 아래 중 하나라도 있으면 그 측정은 무효다.

- 저전압, 클럭 제한, 스로틀링 비트
- 스왑 입출력 1MB 초과
- 다른 프로세스 CPU 평균 5% 초과 (apt·man-db 같은 시스템 타이머가 끼어든 경우가 여기 잡힌다)
- 시작 온도 초과

무효면 같은 밤에 한 번 다시 돈다. 또 무효면 사유와 함께 무효로 남기고 지우지 않는다. 여름 스로틀링 같은 것도 데이터다.

**과열 중단**: 실행 중 CPU가 80°C에 닿으면 그 측정을 바로 멈추고 다시 재지 않는다(architecture.md "실험 중 과열" 가드레일). Pi 4 펌웨어가 클럭을 깎기 시작하는 온도다.

## 8. 전력 (열린 질문 "전력 측정"에 대한 추천)

Pi 4B는 자기 소비 전력을 읽지 못한다. 추천은 **USB-C 인라인 전력계 FNIRSI FNB58**을 Pi 전원 입력에 끼우고, 측정기의 데이터 USB를 Pi에 꽂아 오픈소스 로거([baryluk/fnirsi-usb-power-data-logger](https://github.com/baryluk/fnirsi-usb-power-data-logger), Python, USB HID)로 Pi가 자기 전력을 기록하는 것이다.

- 얻는 것: 유휴 전력, 추론 중 평균 전력, J/토큰, 답 하나당 J, tok/s/W. 다른 Pi 벤치마크(예: Jeff Geerling ai-benchmarks, [reference.md](reference.md))가 전력을 같이 내므로 맞대 볼 수 있다. 블로그 운영 전력(메타 콘텐츠)에도 쓴다.
- 구입 전 확인: 로거가 지금 OS(Python 3.13)에서 도는지. 측정기가 데이터 USB로 Pi에서 전원을 받으면 그 몫이 Pi 소비 전력에 섞이므로 유휴 측정으로 오프셋을 잡는다.
- 사지 않으면: 에너지 열은 비워 두고 온도·클럭만 잰다.

## 9. 결과 형식과 위치

```
experiments/
├── models.toml                  # 모델 목록: 저장소, 리비전, 파일, sha256, 라이선스, 생각 모드 끄는 법 (사람이 고친다)
├── promptsets/llm-tasks-v1/     # 과제 문항·정답(JSONL), 채점 코드, README (CC0)
├── corpora/                     # 퍼플렉서티용 고정 텍스트 (출처·리비전·라이선스 표기)
├── templates/<id>/              # 실행 정의 template.toml (허용 범위, 고정값, 버전)
├── plans/                       # 계획: 밤에 차례로 돌 작업 목록 (예: round1-bench.toml)
├── runner/                      # 러너, 공통 로거, 시작·무효 판정, 요약 통계, 모델 받기, 시험
└── results/<템플릿>/
    ├── summary.csv              # 실행 × 모델 × 조건마다 한 줄. 글과 품질 검사가 보는 값
    └── <실행 ID>/
        ├── conditions.json      # 하드웨어, OS, 커널, llama.cpp 태그·커밋·빌드 옵션, 모델 sha256, 파라미터, 시작 온도, MemAvailable
        ├── bench.jsonl          # llama-bench 원본 출력
        ├── tasks.jsonl          # 문항마다 출력, 점수, TTFT, 토큰 수
        ├── telemetry.csv.gz     # 공통 로거 1초 기록
        └── summary.json         # 평균, 표준편차, 중앙값, p90, 무효 사유
```

- 모델 파일과 llama.cpp 빌드는 레포 밖에 둔다(`~/models/`, `~/opt/llama.cpp/`). 1회차 모델은 SD카드에 약 7GB를 한 번 쓴다.
- 결과는 공개한다. 비밀값이 없고, 기록에 IP나 호스트 이름을 넣지 않는다.
- 커밋: 러너가 매장(`~/unattendant-live`)에서 작성자 Huninn, type `exp`로 커밋·push한다. git 작업은 사이클과 같은 잠금을 쓴다. 러너가 생기기 전의 손 측정은 운영자가 작업실에서 `exp:`로 커밋한다.
- 요약 통계(평균, 중앙값, p90)는 러너가 계산한다. 품질 검사는 글의 측정값을 `summary.csv`와 대조한다(todo.md "품질 검사 확장").

## 11. 비전 (두 번째 트랙)

카메라 없이 시작할 수 있는 런타임 비교부터 한다. 측정 규칙(7절)과 결과 형식(9절)은 LLM과 같다.

**V1. 고정 이미지 벤치마크**

- 이미지: COCO val2017에서 고른 고정 500장(평가)과 따로 고른 200장(INT8 보정). 이미지는 레포에 올리지 않고 ID 목록만 둔다.
- 검출 모델: YOLO26n(Ultralytics, 2026-01), YOLO11n(이전 세대, 기존 Pi 벤치마크와 비교용), RF-DETR nano(Roboflow, Apache-2.0). 분류 모델 MobileNetV3-Small·EfficientNet-Lite0는 나중 GPIO 지연 실험용으로 같이 잰다.
- 런타임: ONNX Runtime, ncnn, LiteRT(XNNPACK), PyTorch(정확도 기준값). FP32와 INT8. 입력 크기 640과 320. Python 3.13 aarch64 휠이 있는지는 설치하며 확인한다.
- 지표: 이미지당 지연(전처리, 추론, 후처리를 나눠서) 중앙값·p99, 처리량, mAP50-95·mAP50(pycocotools, FP32 PyTorch 결과가 기준값), 최대 메모리, 온도, 전력.
- 변환과 INT8 보정은 먼저 Pi에서 해 보고, 무거우면 데스크탑(WOL, Phase 3)으로 넘긴다.
- 라이선스: Ultralytics 패키지는 AGPL-3.0이다. 측정만 하는 것은 문제가 없지만, 그 패키지를 부르는 실험 스크립트를 공개 레포에 둘 때 영향을 따져야 한다(12절 7번).

**V2. 고정 카메라 시리즈**: [edge-ai-blog-topics.md](edge-ai-blog-topics.md) 4-1절. 카메라를 연결한 뒤에 한다.

**V3. GPIO 끝단 지연**: 같은 문서 4-4절. Phase 3.
