# 댓글 기능 구상: giscus vs 자체 댓글 서버

글마다 댓글을 받을 방법 두 가지를 간단히 구상하고 비교한다. 아직 결정 전이라 [architecture.md](../architecture.md)는 고치지 않았다. architecture.md A1은 "댓글은 외부 서비스(giscus 등)를 붙인다"고 가정하고 있으므로, B안을 고르면 그 줄과 가드레일 표도 함께 고쳐야 한다.

- **A안**: giscus. GitHub Discussions를 댓글 저장소로 쓰고, GitHub 로그인 사용자만 댓글을 쓴다.
- **B안**: Pi에서 자체 댓글 서버를 돌린다. 닉네임과 비밀번호만 받고, 비밀번호 해시는 SQLite에 저장한다. 회원가입은 없다.

## 공통 전제

- 사이트는 Hugo 정적 사이트이고, Pi의 Caddy(127.0.0.1:8080)가 Cloudflare Tunnel 뒤에서 서빙한다.
- 댓글 영역은 글 템플릿(`site/layouts/page.html`) 아래에 partial 하나(`_partials/comments.html`)로 붙인다. 글 목록이나 소개 같은 페이지에는 붙이지 않는다.
- 댓글은 외부에서 들어오는 신뢰할 수 없는 텍스트다. Huninn이 댓글을 읽게 할 경우 가드레일은 마지막 절에 따로 적는다.

## A안: giscus (GitHub 로그인)

### 구성

```
브라우저 ──(iframe)──> giscus.app ──(GitHub API)──> Hun0305/unattendant.dev Discussions
```

1. 사이트 레포 `Hun0305/unattendant.dev`(공개)에서 Discussions를 켜고 `Comments` 카테고리를 만든다(Announcement 형식이라 giscus만 새 글을 만들 수 있다).
2. 이 레포에 giscus GitHub App을 설치한다.
3. `_partials/comments.html`에 giscus `<script>` 태그를 넣는다.
   - `data-mapping="pathname"`: 글 URL 경로 하나에 Discussion 하나가 생긴다.
   - `data-lang`: ko 글은 `ko`, en 글은 `en`으로 Hugo 언어에 맞춘다.
   - `data-theme`: 사이트 다크·라이트 모드에 맞춰 `preferred_color_scheme`.
   - `data-loading="lazy"`: 스크롤해서 닿을 때만 불러온다.
4. Pi 쪽에서 새로 돌리는 서비스는 없다.

### 기능

- 댓글, 답글, 수정, 삭제, 이모지 반응, 마크다운을 GitHub가 처리한다. 수정과 삭제는 작성자 본인 GitHub 계정만 할 수 있다.
- 운영자는 레포 관리자 권한으로 댓글 숨김·삭제, Discussion 잠금, 사용자 차단을 할 수 있다.
- 새 댓글 알림은 GitHub 알림(메일)으로 온다. 디스코드로 받으려면 레포 웹훅을 따로 붙인다.

### 장점

- 구현이 거의 없다. 스크립트 태그 하나와 GitHub 설정만 하면 된다.
- 계정이 필요해서 스팸이 매우 적다.
- 비밀번호, IP, 개인정보를 Pi가 저장하지 않는다. 보안 책임이 GitHub에 있다.
- Pi가 꺼지거나 Cloudflare Pages 대기 미러로 바꿔도 댓글은 그대로 동작한다.
- 댓글이 공개 레포 Discussions에 남아 GitHub에서도 보이고 백업된다.

### 단점

- **GitHub 계정이 없는 독자는 댓글을 못 쓴다.** 네이버 블로그를 보고 넘어온 일반 독자에게는 진입 장벽이 크다. 개발자 독자에게는 거의 장벽이 없다.
- giscus.app과 GitHub에 의존한다. giscus가 멈추거나 정책이 바뀌면 댓글도 같이 영향을 받는다.
- 페이지에 외부 iframe과 스크립트가 들어간다. 첫 로딩이 조금 느려지고, 화면 모양을 마음대로 바꾸기 어렵다(테마 CSS 정도만 바꿀 수 있다).
- "Pi가 블로그를 혼자 운영한다"는 이야기에는 보탬이 적다.

## B안: Pi 자체 댓글 서버 (닉네임 + 비밀번호)

### 구성

```
브라우저 ──> Cloudflare Tunnel ──> Caddy :8080 ─┬─ 정적 파일 (site/public)
                                               └─ /api/comments/* ──> 댓글 서버 127.0.0.1:8081 ──> SQLite
```

- **댓글 서버**: `agent/comments/`에 Python 서버(FastAPI 또는 표준 라이브러리 `http.server`)를 둔다. systemd 서비스 `huninn-comments.service`로 돌리고 `MemoryMax`(예: 128M)를 건다. 8081은 지금 비어 있다(2026-10-12 `ss -ltn`으로 확인).
- **Caddy**: 기존 `:8080` 블록에 `handle /api/comments/* { reverse_proxy 127.0.0.1:8081 }`만 추가한다. 터널과 호스트 이름은 바꾸지 않는다.
- **화면**: `_partials/comments.html`에 정적 HTML 폼과 작은 JS를 둔다. 페이지가 열리면 JS가 `GET /api/comments?path=...`로 댓글을 불러온다. 사이트 자체는 계속 정적이다.
- **DB**: `state/comments/comments.db`(SQLite, WAL). 운영 레포 `.gitignore`에 넣고 Pi와 USB 백업에만 둔다.

### 데이터 모델

| 컬럼 | 설명 |
| --- | --- |
| `id` | 정수 키 |
| `path` | 글 URL 경로 (`/posts/xxx/`, `/en/posts/xxx/`) |
| `parent_id` | 답글이면 부모 댓글 id. 답글은 1단계까지만 허용한다 |
| `nickname` | 1\~20자 |
| `body` | 1\~2000자, 순수 텍스트 |
| `pw_hash`, `pw_salt` | 비밀번호 해시와 솔트 |
| `ip_hmac` | 비밀 키로 HMAC한 IP. 속도 제한과 차단에만 쓰고 원본 IP는 저장하지 않는다 |
| `created_at`, `updated_at` | 시각 |
| `status` | `visible`, `deleted`(작성자 삭제), `removed`(운영자 삭제) |

### API

| 요청 | 동작 |
| --- | --- |
| `GET /api/comments?path=` | 그 글의 댓글과 답글 목록. 해시와 IP 정보는 응답에 넣지 않는다 |
| `POST /api/comments` | 새 댓글 또는 답글 (`path`, `parent_id`, `nickname`, `password`, `body`) |
| `POST /api/comments/{id}/edit` | 본문 수정. 비밀번호가 맞을 때만 |
| `POST /api/comments/{id}/delete` | 삭제. 비밀번호가 맞을 때만 |

- 비밀번호가 틀리면 항상 같은 403 응답을 준다. 댓글 하나에 대해 IP별로 틀린 횟수를 세고, 5번 틀리면 일정 시간 막는다.
- 답글이 달린 댓글을 지우면 행은 남기고 "삭제된 댓글입니다"로 표시한다. 답글이 없으면 목록에서 뺀다.

### 비밀번호 처리

- 표준 라이브러리 `hashlib.scrypt`를 쓴다(추가 의존성 없음). 댓글마다 16바이트 랜덤 솔트를 만들고, 파라미터는 `n=2**14, r=8, p=1`(호출당 메모리 약 16MB)로 시작한다. Pi 4에서 한 번 계산하는 시간은 구현할 때 실측해서 이 문서에 적는다.
- 비교는 `hmac.compare_digest`로 한다. 평문 비밀번호는 저장하지도 로그에 남기지도 않는다.
- 대안은 `argon2-cffi`(Argon2id)다. 더 권장되는 방식이지만 패키지가 하나 늘어난다.
- 이 비밀번호는 "이 댓글을 쓴 사람"을 확인하는 정도의 약한 장치다. 독자가 다른 사이트 비밀번호를 재사용할 수 있으니 해시는 반드시 제대로 해야 하고, 폼에 "다른 곳에서 쓰는 비밀번호는 넣지 마세요"라고 안내한다.

### 스팸과 공격 대응

| 위협 | 대응 |
| --- | --- |
| 스팸 봇 | 숨긴 허니팟 입력칸, 폼을 연 뒤 너무 빨리 제출하면 거절, 링크 개수 제한. 그래도 많아지면 Cloudflare Turnstile(무료)을 붙인다 |
| 도배 | IP HMAC 기준 속도 제한 (예: 1분 3개, 하루 30개). IP는 Cloudflare가 넣어주는 `CF-Connecting-IP` 헤더에서 읽는다 |
| 비밀번호 대입 | 댓글별·IP별 실패 횟수 제한. scrypt 비용이 곧 속도 제한 역할도 한다 |
| XSS | 본문은 HTML로 해석하지 않는다. 서버는 텍스트로 저장하고 화면은 `textContent`로만 넣는다. 줄바꿈만 살린다 |
| 서버 과부하 | `MemoryMax`, 요청 본문 크기 제한, 동시에 처리하는 scrypt 계산 수 제한. 댓글 서버가 죽어도 정적 글은 그대로 보인다 |
| 잘못된 `path` | 사이트맵에 있는 글 경로만 받는다 |

### 운영

- **알림**: 새 댓글이 달리면 디스코드에 알린다(기존 알림 경로를 재사용하고, 새 채널이 필요하면 #댓글).
- **운영자 삭제**: Phase 1은 Pi에서 명령으로 한다(예: `comments remove <id>`, `comments ban <id>`). Phase 2에서 디스코드 봇 버튼을 붙인다.
- **비밀값**: IP HMAC용 비밀 키를 `.env`에 추가한다. [pre-commit.md](../pre-commit.md) 규칙대로 gitleaks 규칙이 이 값을 잡는지 확인하고, 필요하면 규칙과 `ops/test-pre-commit.sh` 경우를 추가한다.
- **백업**: `comments.db`를 매일 USB 백업 대상에 넣는다. 쓰기량은 댓글 수만큼이라 SD카드 부담은 작다.
- **고지**: 닉네임과 IP 파생값을 저장한다는 점을 댓글 폼 아래나 소개 페이지에 짧게 적는다.

### 장점

- **로그인 없이 누구나 쓸 수 있다.** 네이버에서 넘어온 일반 독자도 쓸 수 있고, 한국 블로그 독자에게 익숙한 방식이다.
- 데이터와 화면을 전부 직접 가진다. 사이트 디자인에 맞추기 쉽고 외부 스크립트가 없다.
- "Pi가 댓글 서버까지 운영한다"는 이야기가 살아난다. 업타임, 스팸 차단 수 같은 운영 지표가 포트폴리오 소재가 된다.
- Huninn과 연동하기 쉽다. blogops 툴로 바로 감쌀 수 있다.

### 단점

- 만들고 지켜야 할 코드가 생긴다. 서버, 화면, 관리 명령, 테스트, systemd, Caddy, 백업까지 필요하다.
- 보안 책임이 전부 운영자에게 있다. 비밀번호 해시, XSS, 속도 제한 중 하나라도 실수하면 그대로 사고가 된다.
- 스팸을 직접 막아야 한다. 방문자보다 스팸 봇이 먼저 찾아온다.
- Pi나 댓글 서버가 죽으면 댓글도 멈춘다. Cloudflare Pages 대기 미러로 바꾸면 댓글은 동작하지 않는다(읽기 전용 표시만 가능).
- 처음으로 외부에서 쓰기 요청을 받는 공개 엔드포인트가 생긴다. 지금까지는 공개 경로가 전부 읽기 전용이었다.

## Huninn과 댓글 (두 안 공통)

댓글은 누구나 쓸 수 있는 텍스트라 프롬프트 인젝션 통로가 된다. architecture.md 가드레일("외부 텍스트는 데이터로만 다룬다")을 그대로 적용한다.

- 처음에는 Huninn이 댓글을 읽지 않는다.
- 읽게 할 때는 읽기 전용 툴(`list_comments`)로만 준다. 결과는 데이터로 감싸서 넘기고, 댓글 내용이 다른 툴 호출을 일으키지 못하게 한다.
- Huninn이 다는 답글은 글과 같이 초안으로 만들고 승인을 거친다. 승인 모드 해제 기준(게이트 3) 전에는 자동으로 게시하지 않는다.
- Huninn이 쓴 답글에는 작성자를 "Huninn (AI)"로 표시한다.

## 판단 기준

- 지금 독자가 주로 GitHub에서 오는 개발자라면 A가 비용 대비 낫다. 하루면 붙이고 운영 부담이 거의 없다.
- 네이버 쪽 일반 독자의 댓글을 받고 싶거나, 댓글 서버 운영 자체를 블로그 소재로 쓰고 싶다면 B가 맞다.
- 방문자가 아직 적으니 A로 시작하고, 댓글 수요가 확인되면 B로 옮기는 단계적 방법도 있다. 다만 옮길 때 기존 댓글 이전 작업이 생긴다.
