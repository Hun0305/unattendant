# Phase 2 계획: 자율 루프 (C2)

이 문서는 Phase 2에서 **무엇을 어떤 순서로 만들지**를 다룬다. [todo.md](../todo.md) 로드맵의 Phase 2 행과 "다음 단계 준비: Phase 2" 절을 [architecture.md](../architecture.md) 기준으로 풀어 썼다. 설계 근거는 architecture.md에 있다.

계획 초안 (2026-10-07). Phase 1이 아직 진행 중이라, 시작할 때 1절(시작 조건)과 2절(먼저 정할 것)을 다시 본다.

## 한눈에

Phase 2가 끝나면 이렇게 돈다.

- Huninn은 `claude -p` 대신 Messages API를 직접 부르는 자체 루프(C2)로 돈다. 비용은 API 청구 기준으로 남고, 사이클·하루·월 예산 상한은 코드가 지킨다.
- 승인 모드는 그대로 켜져 있다. 운영자는 폰에서 디스코드 #승인 버튼으로 승인·반려한다.
- Pi가 등록된 실험을 밤에 돌리고, Huninn은 그 결과로 실험 글을 쓴다. 소형 LLM이 먼저, 비전이 그다음이다.
- 운영 지표(개입, 장애, 품질 첫 통과율, 비용, 업타임)가 매일 계산돼 공개되고, 상태 띠와 숫자 탭이 실제 값을 보여 준다.
- 게이트 3을 판정할 기록이 쌓인다. 통과하면 승인 모드를 끄고 Phase 3(자동 발행)로 간다.

| Phase 2에서 한다 | Phase 3 이후로 미룬다 |
| --- | --- |
| API 크레딧 전환, C2 루프와 예산 상한 | 승인 모드 해제와 자동 발행 (게이트 3 통과 뒤) |
| 운영 지표와 개입 기록, status.json, 로그 백업 | 공개 운영 현황 페이지 |
| 디스코드 봇 (승인 버튼) | blog-mcp 패키지화, 커뮤니티 배포 |
| 실험 러너와 공통 로거, 첫 실험 글 (LLM → 비전) | WOL 작업 장비 연동(양자화·오프로딩), GPIO 지연 실험, 파인튜닝 |
| Phase 1에서 미룬 툴 (관측, 트렌드, 실험, 공유, 전략 갱신) | SSD 이전, Cloudflare Pages 대기 미러 |
| 비공개 운영 대시보드, 주간·월간 루프 | |

## 1. 시작 조건

Phase 2는 Phase 1이 만든 것 위에 선다. 아래가 끝나야 시작한다.

- [ ] 게이트 2: Huninn이 쓴 글 5편 발행, 품질 첫 통과율 기록 시작
- [ ] 매장(`~/unattendant-live`) 분리와 14:00 타이머가 며칠 동안 문제없이 돈다. C2 루프는 같은 서비스(`huninn-cycle.service`) 자리에 들어간다
- [ ] Huninn이 운영 레포에 커밋·push하는 길 ([blogops.md](../blogops.md) 7절의 `state/` 변경). 지금 코드는 사이트 레포에 발행 커밋만 한다. Phase 2의 전략 갱신, 지표, 실험 결과도 이 길로 나간다
- [ ] 외부 업타임 모니터 → #긴급 웹훅. 업타임과 장애 자동 복구율의 출처다
- [ ] "사람 개입"과 무인 운영의 정의 확정 (todo.md Phase 1 사이트 절). 정의가 있어야 게이트 3을 셀 수 있다
- [ ] 메모리 cgroup 켜기 (sudo, 재부팅)
  - 2026-10-07 확인: 커널 옵션에 `cgroup_disable=memory`가 있고, `/sys/fs/cgroup/cgroup.controllers`에 `memory`가 없다. `cmdline.txt`에는 이 옵션이 없으니 펌웨어가 넣는 기본값이다
  - 그래서 지금 `huninn-cycle.service`의 `MemoryMax=1G`는 효과가 없다. 실험을 `MemoryMax`로 격리한다는 설계(architecture.md, CLAUDE.md 규칙)도 이대로는 안 된다
  - `/boot/firmware/cmdline.txt`에 `cgroup_enable=memory`를 더하고 재부팅한 뒤 다시 확인한다. 바꾼 내용은 ops/에 남긴다

## 3. 만드는 순서

Phase 1의 blogops처럼 설계 문서를 먼저 쓰고 만든다. 게이트 3까지 꼭 거쳐야 하는 길은 굵게 표시했다(API 전환 → 지표·개입 기록 → C2 루프 → 측정 창). 봇, 실험, 대시보드는 그 옆에서 병행한다.

| 순서 | 할 일 | 끝난 기준 |
| --- | --- | --- |
| 1 | **API 전환** (C3 그대로, 인증만 바꾼다) | 14:00 사이클이 API 키로 돌고, 1주 실측 비용이 남는다. 사람의 Pro 한도와 나뉜다. 이 실측이 2절 2·3번의 근거다 |
| 2 | 설계 문서: `docs/loop.md`(C2 루프, 예산, 기록), `docs/experiments.md`(러너, 템플릿, 측정 원칙) | 두 문서가 main에 있고 2절이 정해졌다 |
| 3 | **지표·개입 기록**, status.json, 로그 백업 | 지표가 매일 계산돼 커밋되고, 상태 띠가 실제 값을 보여 준다 |
| 4 | **C2 루프** | 작업실 시험 → C3와 비교 → 매장 타이머 전환. 1주 동안 실패 없이 돈다 |
| 5 | 디스코드 봇 | 폰에서 승인·반려가 되고, 해시가 다르면 거부되는 것을 확인 |
| 6 | 실험 러너와 LLM 첫 실험 | 야간 실험 → 결과 CSV 커밋 → 첫 실험 글이 수치 대조 품질 검사를 통과 |
| 7 | 관측·트렌드·공유 툴, 대시보드, 주간 루프 확장 | 주간 보고서에 방문·검색 통계와 실제 비용이 들어가고, 전략 갱신이 한 번 돈다 |
| 8 | 비전 실험, 월간 루프 | 정기 촬영과 첫 비전 글. 기준 실험을 다시 돌려 기존 글을 갱신 |
| 9 | **게이트 3 측정 창** (14일) | 5절 기준을 넘으면 승인 모드 해제를 결정 |

### 4.2 C2 루프와 예산 상한

설계는 `docs/loop.md`에 먼저 쓴다. 핵심은 architecture.md 권장 조합대로 툴 로직을 blogops 하나에 두고, MCP 서버와 C2 루프가 같이 쓰는 것이다.

**툴 공유**

- [ ] 툴의 이름·설명·입력 스키마와 호출 검사·기록(`CycleGuard`, `logs/YYYY-MM-DD.jsonl`)을 한 곳에 둔다. 지금은 `server.py`의 `@tool`과 MCP 등록이 한데 묶여 있다
- [ ] MCP 서버는 남긴다. 운영자가 Claude Code 등에 붙여 손으로 운영할 때 같은 툴과 같은 검사를 쓴다

**요청과 대화 기록** (Claude Sonnet 5.5 기준, 2026-10-07 API 문서로 확인)

- [ ] `anthropic` Python SDK를 의존성에 더한다. 루프는 가칭 `agent/blogops/loop.py`
- [ ] `model`과 `output_config.effort`를 늘 명시한다. thinking은 기본(adaptive)을 쓴다. 이 모델에서 `thinking: {"type": "disabled"}`와 강제 `tool_choice`(`any`, `tool`)는 400이다
- [ ] 대화 기록은 덧붙이기만 한다. 응답 `content`를 thinking 블록까지 그대로 돌려보내고, 사이클 중에 system 프롬프트, 툴 목록, 앞 메시지를 바꾸거나 자르지 않는다. 앞부분이 바뀌면 thinking 블록이 무효가 되고, 2026-08-31 이후 만든 계정에서는 400이 난다. 길어질 결과는 툴이 처음부터 짧게 돌려준다
- [ ] 프롬프트 캐시: system(prompt.md)과 툴 정의 끝에 캐시 지점을 둔다. 날짜와 사이클 ID는 지금처럼 첫 user 메시지에 둔다(system에 넣으면 매번 캐시가 깨진다). 두 번째 요청부터 `cache_read_input_tokens`가 0보다 큰지 테스트로 확인한다
- [ ] 툴 호출 60회 상한은 그대로 두고, 요청 수 상한을 따로 둔다

**멈추는 조건** (`stop_reason`)

- [ ] `tool_use`: 툴을 실행하고 결과를 모두 다음 user 메시지 하나에 `tool_result`로 돌려준다. 실패한 툴은 `is_error: true`로 돌려준다
- [ ] `end_turn`: 사이클 끝
- [ ] `max_tokens`: 그 턴의 툴은 실행하지 않는다(입력이 잘렸을 수 있다). `max_tokens`를 올려 한 번 다시 하고, 또 그러면 실패로 끝낸다
- [ ] `refusal`: 툴을 실행하지 않고 멈춘다. `stop_details`의 분류를 기록하고 #긴급으로 알린다. 안전 분류기가 문제없는 요청을 거절할 때도 있어서, 서버 쪽 대체 모델(`fallbacks: "default"`, beta)을 켤지 설계 문서에서 정한다. 켜면 대체로 처리된 요청의 모델과 단가를 따로 기록한다
- [ ] 그 밖(`pause_turn` 등): 서버 툴을 쓰지 않으므로 오류로 본다

**비용과 예산**

- [ ] 요청마다 `usage`(입력, 출력, 캐시 쓰기, 캐시 읽기 토큰)를 `logs/`에 남기고 단가표로 달러를 계산한다. 단가는 `config.py`에 두고 가격이 바뀌면 고친다. Sonnet 5.5는 100만 토큰당 입력 $2, 출력 $10, 캐시 쓰기 $2.50(5분), 캐시 읽기 $0.20
- [ ] 요청 전에 사이클·하루·월 누적을 보고, 상한(2절 3번)을 넘으면 요청하지 않고 멈춘 뒤 #긴급으로 알린다
- [ ] 예산 상한은 설정 파일에만 있고, Huninn의 툴로는 바꿀 수 없다
- [ ] Console 한도에 걸렸을 때 루프가 다시 시도하지 않고 #긴급으로 알리는지 확인한다 (claude-billing.md에는 400 오류로 멈춘다고 적혀 있다)

**실패 처리**

- [ ] 429·5xx·529: SDK 재시도(기본 2회) 뒤에도 실패하면 사이클을 실패로 끝내고, 1시간 뒤 한 번만 다시 돈다. 그것도 실패하면 그날은 쉬고 #긴급. 다시 돌아 성공하면 장애 자동 복구로 센다
- [ ] 인증·권한·결제·한도 오류: 다시 돌지 않고 #긴급(critical)
- [ ] `cycle.py`에서 그대로 가져온다: 한 번에 하나(잠금), 25분 제한, `cycles.jsonl` 기록과 실패 알림, `BLOGOPS_NO_PUBLISH` 시험 실행, `--show`

**프롬프트와 전환**

- [ ] 설정 하나(`approval_mode`)로 바뀐다. 끄면 `publish_post`가 승인 대신 품질 통과 해시만 확인하고, 품질을 통과한 초안을 같은 사이클에 발행할 수 있다. 하루 1편과 나머지 검사는 그대로다
- [ ] 끈 상태에서는 #승인 요청 대신 발행 뒤 #일일요약으로 사후 알림을 보낸다
- [ ] 시험 실행(`BLOGOPS_NO_PUBLISH`)으로 끈 상태의 흐름을 확인한다
- [ ] 발행한 글을 사람이 내리는 절차를 ops/README.md에 적는다 (`unpublish_post`는 사람만 한다)
