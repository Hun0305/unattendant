# Pi 상태 파일 (status.json)

사이트 상단 상태 띠와 통계 탭의 "지금 Pi"가 읽는 파일이다. Pi가 5분마다 CPU 온도, 메모리, 디스크 여유, 가동 시간을 쓴다. 무인 운영을 시작하기 전에도 돌고, 연속 무인 운영일과 오늘 비용은 개입 기록과 환율이 정해진 뒤에 더한다. 원래 Phase 2 항목이었고 2026-10-14에 Phase 1로 앞당겼다. 진행은 [todo.md](todo.md) "사이트" 절에서 본다.

- 이 파일은 "Pi 안에서 잰 값"이다. 사이트가 밖에서 열리는지(업타임)는 [uptime.md](uptime.md)의 외부 모니터가 잰다. Pi가 죽으면 이 파일도 멈추고 사이트도 같이 안 열리므로, "죽었다"는 이 파일로 알 수 없다.

## 1. 구성

```
[Pi] huninn-status.timer(5분) → status.py → /run/huninn/status.json (RAM)
        Caddy :8080 /status.json ─▶ Cloudflare(캐시 안 함) ─▶ 브라우저
                                        └ 상태 띠(모든 페이지 맨 위)와 통계 탭 "지금 Pi"가 읽는다
```

## 2. 정한 것

| 정한 것 | 내용 | 이유 |
| --- | --- | --- |
| 위치 | `/run/huninn/status.json` (tmpfs) | 5분마다 쓰는 파일이라 RAM에 두면 SD카드 쓰기가 없다. 발행 빌드가 `public/`을 비우므로 거기에는 못 둔다. 재부팅하면 비워지지만 타이머가 부팅 1분 뒤 다시 쓴다 |
| 실행 | systemd 타이머와 oneshot 서비스 | 상주 프로세스 없이 5분마다 한 번 돌고 끝난다. 메모리 상한 64MB |
| 서빙 | Caddy `:8080`과 미리보기 `:8081`의 `/status.json`만 `/run/huninn`에서 내준다 | 미리보기 페이지의 상태 띠도 같은 파일을 읽는다 |
| 캐시 | 응답에 `Cache-Control: no-store`, 브라우저도 `no-store`로 요청 | 몇 분 전 값이 남아 "지금"으로 보이면 안 된다. Cloudflare는 `.json`을 기본으로 캐시하지 않는다 |
| 공개 범위 | 온도, 메모리, 디스크 여유, 가동 시간, Huninn 마지막 사이클의 시각·성공 여부(2026-10-27 추가) | IP, 호스트 이름, 프로세스, 버전, 사이클 오류 문장은 넣지 않는다 |
| 읽지 못한 값 | 필드를 뺀다 | 화면이 없는 값은 알아서 숨긴다 |

## 3. 파일 형식

```json
{
  "updated": "2026-10-14T00:35:00+09:00",
  "cpu_temp_c": 39.4,
  "mem_used_gb": 1.7,
  "mem_total_gb": 3.7,
  "uptime_s": 105670,
  "disk_free_pct": 69.8
}
```

| 필드 | 뜻 | 읽는 곳 |
| --- | --- | --- |
| `updated` | 쓴 시각(한국 시간) | `/sys`·`/proc`가 아니라 시계 |
| `cpu_temp_c` | CPU 온도 | `/sys/class/thermal/thermal_zone0/temp` |
| `mem_used_gb`, `mem_total_gb` | 사용 중, 전체. 사용 중은 전체에서 `MemAvailable`을 뺀 값이라 캐시는 쓴 것으로 세지 않는다 | `/proc/meminfo` |
| `uptime_s` | Pi가 켜진 뒤 지난 초(통계 탭의 "가동 시간") | `/proc/uptime` |
| `disk_free_pct` | 루트 파일시스템의 여유 비율 | `shutil.disk_usage("/")` |
| `cycle` | Huninn의 마지막 정규 사이클: `at`(기록 시각), `ok`(성공 여부). 실패면 `fail_streak`(연속 실패 횟수), `failing_since`(그 첫 실패 시각)가 붙는다. 시험 실행(`dry_run`)은 뺀다. 기록이 없으면 필드가 없다 (2026-10-27) | `logs/cycles.jsonl`의 `ts`, `is_error` |

사이트가 더 읽는 필드(`unattended_days`, `cost_today_krw`)는 아직 쓰지 않는다. 전체 형식은 site 레포의 README에 있다.

## 4. 화면이 하는 일

| 상태 | 상태 띠 | 통계 탭 "지금 Pi" |
| --- | --- | --- |
| 정상 | 켜진 점, "운영 준비 중", CPU, 메모리, "HH:MM 갱신" | 4칸 값과 마지막 갱신 |
| 파일 없음(재부팅 직후, 타이머 중지) | 빈 점과 "운영 준비 중"만 | "불러오지 못했습니다" 안내 |
| 30분 넘게 갱신 없음 | 빈 점과 "갱신 멈춤", 마지막 값 | 마지막 값과 갱신 시각 |
| Huninn 사이클 실패, 또는 26시간 넘게 사이클 없음 | 켜진 색의 빈 고리, "운영 준비 중" 대신 "Huninn 멈춤 · 10월 17일부터 11회 연속 실패"(또는 "Huninn 실행 지연 · 마지막 10월 25일"), CPU, 메모리 | "Huninn 마지막 실행" 줄에 시각과 결과 |
| `unattended_days` 있음(앞으로) | "운영 준비 중"이 사라지고 연속 무인 운영일이 보인다 | 같음 |

무인 운영 전에는 `unattended_days`가 없어 띠에 "운영 준비 중"이 값과 함께 남는다.

`cycle`을 더한 이유: 2026-10-17부터 구독 토큰 취소로 사이클이 매일 실패했는데, 띠는 Pi가 살아 있다는 것만 보여 켜진 점과 "운영 준비 중"을 11일 동안 그대로 띄웠다. 점은 Pi(상태 파일)를, 띠 문구는 Huninn을 말하게 나눴다.

## 5. 켜는 순서

PR이 main에 합쳐지고 매장이 받은 뒤, sudo가 필요한 단계(유닛 설치, 타이머 켜기, Caddy 재시작)를 한다. 명령은 [ops/README.md](../ops/README.md) "Pi 상태 파일"에 있다. Caddy 재시작 때 블로그가 1~2초 끊기고, 그 순간을 업타임 모니터가 잡으면 #긴급에 Down·Up 알림이 한 쌍 올 수 있다.

## 6. 확인한 것 (2026-10-14, 설치 전)

- `status.py` 단위 테스트 12개(필드 형식, 읽지 못한 값, 원자적 쓰기와 권한 0644, 종료 코드). 전체 178개 통과.
- 실제 Pi에서 한 번 실행해 값이 읽히는 것(온도, 메모리, 디스크, 가동 시간).
- 새 Caddyfile을 임시 포트에 띄워, 상태 파일 경로를 뺀 모든 경로가 옛 설정과 상태·헤더·본문이 같은 것. `/status.json`은 200, `no-store`, JSON이고 파일이 없으면 404, POST는 405.
- `systemd-analyze verify`가 두 유닛을 통과.
- 헤드리스 Chromium으로 실제 사이트 빌드를 열어 정상, 파일 없음, 오래됨, 무인 운영일 있음 네 경우의 띠를 확인(데스크톱과 390px 폭). 영어판 라벨은 빌드 결과로만 확인했다.

설치 뒤에 확인할 것: 공개 URL의 `/status.json`이 200이고 `cf-cache-status`가 `HIT`이 아닌 것, 브라우저에서 띠와 통계 탭, 타이머를 멈췄을 때 30분 뒤 "갱신 멈춤", 재부팅 뒤 1~2분 안에 값이 돌아오는 것.

## 7. 나중에

- `unattended_days`와 `cost_today_krw`: 개입 기록과 고정 환율이 정해진 뒤([todo.md](todo.md) Phase 2 "운영 지표, 개입 기록, 백업").
- 경고 색: CPU 75°C 이상, 디스크 10% 미만처럼 임계값을 넘으면 점을 다른 색으로 바꾸는 `state` 필드. 디자인 문서에서 노랑은 광고 표시 전용이라 새 색을 정해야 하고, 값이 쌓인 뒤에 정한다.
- 업타임 가용률(%)을 띠나 통계 탭에 같이 보이는 것은 [uptime.md](uptime.md)의 내보내기가 생긴 뒤.
