# 외부 업타임 모니터

Pi 밖에서 사이트를 5분마다 열어 보고, 열리지 않으면 디스코드 #긴급으로 알린다. 같은 측정이 업타임(가용률)과 장애 기록의 출처다. 설계는 2026-10-13에 정했고, 켜는 일은 운영자가 한다. 진행은 [todo.md](todo.md) Phase 1 "Phase 0에서 넘어온 것"에서 본다.

- **업타임**: 외부 모니터가 잰, 사이트가 정상이었던 시간의 비율. 최근 30일과 전체 기간. 계획한 재부팅도 빼지 않는다.
- **장애**: 외부 모니터가 5분 간격으로 두 번 연속 응답을 받지 못함. 소개 페이지에 공개한 정의 그대로다. 알림은 첫 Down에 가고, 장애로 세는 건 기록을 계산할 때 연속 2회를 볼 때다.
- 통계 탭의 "가동 시간"은 Pi가 켜져 있던 시간이라 이 문서의 업타임과 다른 값이다.

## 1. 구성

```
[외부] UptimeRobot ─ 5분마다 접속 ─▶ Cloudflare ─▶ 터널 ─▶ Caddy :8080 ─▶ site/public
          │
          ├─ Down / Up ─▶ 디스코드 웹훅 ─▶ #긴급 ─▶ 운영자 폰      (Pi를 거치지 않는다)
          ├─ 공개 상태 페이지 (UptimeRobot 주소)
          └─ 하루 1회 읽기 전용 조회 ◀─ [Pi] uptime.py (예정, 7절)
```

- 알림 경로는 Pi를 거치지 않는다. Pi가 죽어도 알림이 가야 해서다. Pi에 웹훅 수신 주소를 만들지 않으므로 터널로 열리는 길도 늘지 않는다.
- 기록은 Pi가 외부 서비스에서 가져온다(pull).
- 사이클 때 `get_system_health`가 보는 사이트 응답은 Pi 안에서 하루 한 번 보는 것이라 이 모니터를 대신하지 못한다.

## 2. 정한 것

| 정한 것 | 내용 | 이유 |
| --- | --- | --- |
| 서비스 | UptimeRobot 무료 | 모니터 50개, 5분 간격, 디스코드 연동이 전 플랜에 있다. 약관이 상업·업무 용도를 포함한 모든 용도를 허용한다 |
| 알림 연동 | 디스코드 연동 (일반 웹훅 아님) | 일반 웹훅은 유료(Team 이상)다. 그래서 메시지 모양과 멘션을 못 정하고, 폰에서는 #긴급 채널 알림을 "모든 메시지"로 둔다 |
| 모니터 | 1개: 홈 키워드 | 상태 코드만 보면 "200인데 빈 페이지"를 놓친다. 이 모니터가 공개 업타임의 유일한 기준이다 |
| 안 거는 것 | preview 호스트, RSS, `/en/`, SSL·도메인 점검(무료에서는 안 된다) | preview는 추측할 수 없는 토큰 경로라 공개 페이지에 닿으면 안 된다. RSS·`/en/`은 같은 빌드라 새 실패 유형이 없다 |
| 공개 | 공개 상태 페이지를 처음부터 연다 | 운영 지표를 공개하는 방침과 맞고, 외부 서비스가 잰 값이라 우리가 고칠 수 없다. 처음 값이 흔들려도 그대로 둔다. 일주일 뒤에 열자는 안은 쓰지 않았다 |

## 3. 설정값 (다시 만들 때 보는 표)

화면 이름은 서비스 쪽에서 바뀔 수 있다.

**모니터**

| 항목 | 값 |
| --- | --- |
| 이름 | `unattendant.dev` (공개 페이지에 그대로 보인다) |
| 종류 | Keyword |
| 주소 | `https://unattendant.dev/` |
| 키워드 | `Huninn` (홈에 13번 나온다. 2026-10-13 확인) |
| 알림 조건 | 키워드가 없을 때 |
| 간격 | 5분 (무료 최소) |
| 알림 대상 | 디스코드(#긴급)와 이메일. 이메일은 끄지 않는다. 디스코드가 안 될 때의 이중화다 |

홈은 `cf-cache-status: DYNAMIC`이라 Cloudflare 캐시가 원본 장애를 가리지 않는다(2026-10-13 확인). 이 값이 `HIT`으로 바뀌는 캐시 규칙을 만들면 모니터가 장애를 놓친다.

**디스코드 연동**

- Integrations & API → Discord → Add. 웹훅 URL은 Phase 0에서 만든 #긴급 웹훅이다. 디스코드 채널 설정 → 연동 → 웹훅에서 복사해 붙인다. 값을 터미널·채팅·문서에 쓰지 않는다.
- 받을 사건: Up events, Down events. 이름(Friendly name)은 `Discord integration #1`이다.
- 멘션: 연동의 Custom value 칸에 `<@운영자 디스코드 숫자 ID>`를 넣는다. 이름(`<@이름>`)은 글자 그대로 찍힐 뿐 멘션이 안 된다. ID는 `huninn.env`의 `DISCORD_OWNER_ID`와 같다. 2026-10-13에 멘션이 되는 것을 확인했다.
- 디스코드 앱: #긴급 알림을 "모든 메시지"로 해 두면 멘션이 빠져도 알림이 온다.

**공개 상태 페이지**

- 무료 1개, 주소는 UptimeRobot 것이다(우리 도메인은 유료).
- 넣는 모니터는 `unattendant.dev` 하나다. "전체 선택"을 하지 않는다. 시험용 임시 모니터와 preview 호스트가 공개 페이지에 뜨면 안 된다.
- 가용률과 응답 시간을 보여 주는 항목이 있으면 켠다.

## 4. 켜는 순서 (운영자, 약 20분)

1. UptimeRobot 계정을 만들고 2단계 인증을 켠다. 계정은 하나만 쓴다(약관).
2. 디스코드 연동을 붙인다(3절).
3. 모니터를 만든다. 몇 분 안에 첫 확인이 Up이어야 한다. Down이면 Cloudflare 보안 설정이 프로브를 막는지 본다(2026-10-06 기준 Bot fight mode와 AI Labyrinth는 꺼 둔 상태).
4. 5절대로 시험하고 임시 모니터를 지운다.
5. **시험이 끝난 뒤에** 공개 상태 페이지를 만든다. 시험 장애가 공개 기록에 남지 않게 하는 순서다.
6. 모니터를 만든 시각과 상태 페이지 주소를 7절 표에 적는다.

## 5. 시험

서비스를 멈추지 않는다.

1. 임시 모니터를 하나 더 만든다. 주소는 홈, 키워드는 절대 없을 글자(예: `zzz-없는-단어`), 조건과 알림 대상은 위와 같게 한다. 없는 주소(404)를 쓰지 않는 건 404 페이지에도 `Huninn`이 있어 Down이 안 날 수 있어서다.
2. 몇 분 안에 #긴급에 Down 메시지가 오는지, 폰 알림이 울리는지 본다.
3. 임시 모니터의 키워드를 `Huninn`으로 고쳐 Up 메시지가 오는지 본다.
4. 임시 모니터를 지운다. 두 모니터의 이름이 같아 헷갈리니, 지우기 전에 임시 쪽 이름부터 바꿔 둔다.

2026-10-13에 이렇게 시험했다. Down·Up 메시지가 모두 #긴급에 왔고 멘션도 됐다.

실제 장애에서 Cloudflare가 오류 화면(530·502)을 돌려주면 키워드가 없어 Down으로 잡힐 것이다. 이건 실제 장애 때 확인하고 여기에 적는다.

## 6. 운영 규칙

- 재부팅이나 Caddy·터널 재시작 같은 계획한 작업에서도 Down·Up 알림이 올 수 있다. 무료에는 점검 시간대 기능이 없고, 업타임에서도 빼지 않는다. 계획한 작업은 소개 페이지 정의대로 "사람 변경"으로 따로 기록한다.
- 웹훅 URL은 비밀값이다(가진 사람은 #긴급에 글을 쓸 수 있다). 새면 디스코드에서 그 웹훅을 지우고 새로 만든 뒤, UptimeRobot 연동의 URL과 `huninn.env`의 `DISCORD_WEBHOOK_URL`을 바꾼다. gitleaks에 `discord-webhook-url` 규칙이 있다.
- 모니터는 새로운 실패 유형을 잡을 때만 늘린다. 업타임의 기준은 계속 홈 모니터 하나다.
- 약관은 UptimeRobot 데이터·상태 페이지·API 응답을 모니터링 서비스로 다시 팔거나 포장하는 것을 막는다. 우리는 이 사이트의 가용률을 지표로 공개할 뿐이다.

## 8. 설정 화면에서 확인할 것

**확인됨 (2026-10-13 설정 화면)**

- 알림 지연("No delay"), SSL·도메인 점검, 위치 추가는 유료(왕관 표시)다. 알림은 첫 Down에 바로 간다.
- 멘션은 Custom value 칸으로 된다(3절).
- 홈 모니터가 Up이다. Cloudflare가 프로브를 막지 않는다.

**아직 모르는 것**

- 몇 번 재시도한 뒤 Down으로 판정하는지(도움말은 3회로 설명한다)
- 무료 공개 상태 페이지가 보여 주는 것: 일 단위 막대의 기간, 가용률, 장애 이력, 응답 시간. 페이지가 스크립트로 그려져 문서 도구로는 못 읽었다. 운영자가 화면에서 보고 적는다.
- v3 API에서 읽기 전용 키가 어떻게 쓰이는지, 장애·가동률 조회 경로(서드파티 요약에서 `GET /v3/incidents`와 `GET /v3/monitors/uptime-stats`를 봤을 뿐 공식 문서로는 못 봤다)

## 9. 결정 기록 (2026-10-13)

- UptimeRobot 무료, 디스코드 연동, 모니터 1개(홈 키워드), 알림은 Pi를 거치지 않는다.
- 소개 페이지의 업타임 뜻을 "5분마다 확인한 결과 중 성공한 비율"에서 "정상이었던 시간의 비율"로 바꿨다. UptimeRobot의 값이 시간 기준이라서다.
- 공개 상태 페이지는 일주일 뒤가 아니라 처음부터 연다. 2026-10-13 21:37에 만들었고, 통계 탭과 소개 페이지의 업타임 행에서 링크한다.
- 통계 탭 "지금 Pi"의 "업타임"을 "가동 시간"으로 바꿔 업타임이 가용률 하나만 가리키게 했다(사이트 레포 `e6e9a76`).
